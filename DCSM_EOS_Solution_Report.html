關鍵判斷

  1. 真正的斷點是 2029-01，不是 2027-10。CRM v9.1 地端版與 Windows Server 2019 在 2029-01 前後停止支援，而且 v9.1 之後沒有地端版本可升級。要決定的是何時、用什麼方式離開 CRM，而不是要不要離開。
  2. 先決定 CRM 的去留，SQL 的處理方式就跟著決定。CRM 有兩個建議方案，二擇一：P5 不做 CRM 系統，客戶移管、銷戶等功能回歸徵審系統，我方只做資料報表；徵審系統基本能承接，CRM 有機會在 2027-10-12 前下架，SQL 2017 即不需處理。P2 仍需保留系統時由行內精簡客製核心功能；新系統約 2028 Q4 上線，SQL 2017 必須另外處理。
  3. CRM 無法在 2027-10-12 前下架時，SQL 才需處理。兩個選擇：S4 延用 SQL 2017 到 CRM 下架（需申請展延）；或 S1 在 2027-10-12 前平行搬遷到 SQL Server 2019。S1 的本質是「買保險」：搬遷工作只服務 CRM 下架前的剩餘期間，下架越有把握、越早，S1 越像浪費人力。
  4. 各方案的主要風險不同。P5：時程依賴徵審系統負責單位，需書面承諾。P2：行內兩人可用產能約 26–33 人月，遠低於傳統估算，須先與法金業務窗口協調精簡範圍。S1：行內沒有任何 2017 轉 2019 的經驗（UAT 是直接安裝在 2019）。S4：延用期間沒有安全性更新，屬稽核缺失。

P2 前置議題：與法金業務窗口協調精簡範圍

P2 能否在兩人產能內完成，關鍵在範圍。執行 P2 時，須先與法金業務窗口協調，將現行 CRM 的使用內容精簡後，取出核心功能再進行客製開發。

  1. 盤點現況以 CRM 使用紀錄與客製項目（欄位、workflow、外掛、報表）整理現行使用內容與使用頻率；可用 Copilot 輔助。
  2. 逐項分類與法金業務窗口逐項確認：保留為核心、精簡後保留、改由報表提供、停用。
  3. 簽核核心功能法金業務窗口與主管簽核核心功能清單與第一階段範圍；未列入者列為第二階段或停用。
  4. 對照產能以核心功能清單估算工作量，對照兩人可用產能約 26–33 人月。
  5. 客製開發只針對核心功能開發；新增需求走變更管理，不在開發中途擴大範圍。
協調風險：業務端傾向「全部保留」 精簡需要業務單位接受部分功能停用或改變做法，需主管支持並訂定簽核期限（建議 2027-03-31 前）。範圍未能收斂時，依 2027-06-30 決定點增補人力，或將部分功能移到第二階段；CRM 在 2029-01 停止支援，不能以延長 CRM 使用作為退路。
優勢：訪談範圍遠小於 P3 統籌熟悉現行 CRM 與業務流程，能直接與法金窗口討論取捨。

若採 S1：平行搬遷的做法

以下四節只在採用 S1 時適用（路線 C，或路線 E 下架來不及且 S4 展延未獲核准）。

  1. 建置目標主機SQL Server 2019（最新 CU）裝在 Windows Server 2022 上，OS 支援到 2031-10；CRM 下架後可直接轉為封存庫主機。
  2. 事先還原 6 TB上線前幾天，把正式環境完整備份（含差異備份）以 NORECOVERY 還原到新主機。最花時間的作業在停機前完成。
  3. 持續同步交易記錄以 log shipping（Standard 版支援）持續套用，並和現行備份排程整合，避免打斷記錄鏈。
  4. 停機切換停止 CRM 與外部寫入，原主機備份最後一段交易記錄並套用到新主機，再把 CRM 改指向新主機。停機預估約 1–3 小時加驗證，以演練量測為準。
  5. 開放前驗證使用者寫入任何新資料前，由 IT 與業務代表完成核心功能驗證。此時切回，零資料遺失。
  6. 保留原主機 30 天原 SQL 2017 停止寫入但完整保留（9 月切換時最晚保留至 2027-10-12），開放後出重大問題仍有切回點。
注意事項 資料庫在 SQL 2019 完成還原後就無法再還原回 SQL 2017，所以原主機必須保留，切換前後不得升級、修補或改設定。相容性層級初期維持 140，穩定後再評估調到 150。CRM 改指向新主機建議走官方程序：修改各 CRM 伺服器登錄檔的 configdb，並用 Deployment Manager 改組織設定；以連線別名承接原主機名稱是常見做法，但不在 CRM 官方程序內。

資料：6 TB 盤點與封存

不論走哪條路線，CRM 下架時都需要封存歷史資料；走 P5 時客戶資料要轉入徵審系統，走 P2 時有效資料要轉入新系統，走 S1 時要搬遷整個資料庫。先盤點並清理 6 TB，可以同時降低這些工作的時間與風險。CRM 資料庫的體積通常集中在系統作業、稽核與附件資料表，不一定是業務資料。清掉非業務資料，SQL 搬遷與新系統轉檔的時間和風險都會下降。

資料表內容處理方式
AsyncOperationBase
WorkflowLogBase		系統作業、workflow 執行紀錄用 Bulk Delete 等官方方式清理已完成的作業
AuditBase稽核紀錄依法規保存年限，先匯出封存再刪除
AnnotationBase
ActivityMimeAttachmentBase		存在資料庫內的附件新系統改用檔案儲存；舊附件轉檔或封存
PrincipalObjectAccess共用與權限紀錄檢查是否異常成長
 
SELECT TOP (30)
    s.name AS schema_name,
    t.name AS table_name,
    SUM(CASE WHEN p.index_id IN (0, 1) THEN p.rows ELSE 0 END) AS row_count,
    CAST(SUM(a.total_pages) * 8 / 1024.0 / 1024 AS DECIMAL(10, 2)) AS total_gb
FROM sys.tables t
JOIN sys.schemas s ON s.schema_id = t.schema_id
JOIN sys.partitions p ON p.object_id = t.object_id
JOIN sys.allocation_units a ON a.container_id = p.partition_id
GROUP BY s.name, t.name
ORDER BY total_gb DESC;

只用 CRM 官方支援的方式清理，不要直接對資料表下 DELETE；刪除前確認內部保存政策與法規保存年限。

封存庫（走 S1）

SQL 2019 主機直接轉為唯讀封存庫；2030-01 前再把封存資料庫還原到較新版 SQL。

封存庫（走 S4，或路線 E 在 2027-10-12 前下架）

CRM 下架時把最終備份離線還原到新系統或報表平台所用的 SQL（2022 以上）作為唯讀封存庫。
